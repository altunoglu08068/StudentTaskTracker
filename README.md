# StudentTaskTracker

A console-based task and team management application designed for student teams, built with C# and .NET.

## Overview
StudentTaskTracker helps student project teams organize tasks, assign responsibilities, and monitor workflow status across clear lifecycle stages.

## Features
- Add and list team members, including their name, email, and role.
- Create tasks with a title, description, and due date.
- List all tasks and see their status and assigned member.
- Assign a task to a team member, report whether the task or member was not found, and list tasks assigned to a specific member.
- Update a task's status: `Backlog`, `InProgress`, `InReview`, or `Done`.
- Validate positive numeric IDs and status selections in the interactive menu.
- Persist tasks and team members in a SQLite database using Entity Framework Core.

## Project Structure
- `Models/`: Core domain models representing business entities.
  - `TaskStatus.cs`: Enum defining task stages (`Backlog`, `InProgress`, `InReview`, `Done`).
  - `AssignTaskResult.cs`: Enum defining task assignment outcomes (`Success`, `TaskNotFound`, `MemberNotFound`).
  - `TeamMember.cs`: Model representing student team members.
  - `ProjectTask.cs`: Model representing assigned tasks with deadlines and status.
- `Data/`: EF Core persistence layer.
  - `AppDbContext.cs`: SQLite database context and relationship configuration.
- `Services/`: Business logic for managing team members and tasks.
  - `TaskManager.cs`: CRUD and assignment operations for the application.
- `Migrations/`: Database schema migration files generated by EF Core.
- `Program.cs`: Interactive console menu and user input handling.

## Tech Stack

## How to Run Locally
Requires the .NET 10 SDK.

```bash
dotnet restore
dotnet build
dotnet run
```

The application stores tasks and team members in a SQLite database named `student_tasks.db` in the project directory. When used for the first time, EF Core creates the database file and schema automatically if needed.

## Database
The application uses SQLite with the `AppDbContext` configuration in `Data/AppDbContext.cs`. The database file is created in the project root as `student_tasks.db`.

The migration files under `Migrations/` are included for schema versioning and can also be applied manually with:

```bash
dotnet ef database update
```

## Time Complexity
Let **N** be the number of tasks, **M** the number of team members, and **K** the number of tasks assigned to the selected member. Complexity below assumes SQLite uses its primary-key and foreign-key indexes. Database I/O and console output add machine-dependent overhead.

| Operation | Best case | Worst case |
|---|---:|---:|
| Reject duplicate member ID | O(1) | O(log M) |
| Add a unique member (check and insert) | O(log M) | O(log M) |
| Reject duplicate task ID | O(1) | O(log N) |
| Add a unique task (check and insert) | O(log N) | O(log N) |
| Update task status (ID lookup and update) | O(1) | O(log N) |
| Assign a task to a member (two ID lookups and update) | O(1) | O(log N + log M) |
| List all members | O(M) | O(M) |
| List all tasks | O(N) | O(N) |
| List a member's tasks (indexed foreign-key lookup) | O(log M + log N) | O(log M + log N + K) |

Best-case indexed lookups find the record immediately; worst-case lookups traverse the index. Listing operations must visit and print every returned record. Actual execution time depends on database size, storage, and console output; no fixed runtime is guaranteed.

Updating a task or assigning it also includes a database write. Best-case figures describe immediate index access; actual database I/O and console output can dominate these algorithmic costs.
